## 2. 本轮最重要的产出：抓到一个会污染所有胜率的引擎 bug

### 现象

加入**镜像自检**（同阵容打自己，期望 ≈50%）后：

```
236 vs 236  ->  红胜 88%
246 vs 246  ->  红胜 100%
```

**红方有结构性优势。** 在这条修好之前，任何胜率数字都是假的。

### 根因

`kernel/timeline.ts` 的 `TieBreaks.SPEED_THEN_RANDOM`：

```ts
fn: (c) => c.slice().sort((a, b) => b.velocity() - a.velocity())[0]
```

名字叫 SPEED_THEN_**RANDOM**，但**从头到尾没有用随机数**。JS 的 `sort` 是稳定排序，
所以速度相同时永远返回**插入顺序最靠前**的那个 —— 而红方永远先注册。
结果是：所有同速并列都判给红方。

### 修复

```ts
fn: (c, rng) => {
  const maxV = Math.max(...c.map(e => e.velocity()));
  const fastest = c.filter(e => Math.abs(e.velocity() - maxV) < 1e-9);
  if (fastest.length === 1) return fastest[0];
  return (rng?.pick(fastest)) ?? fastest[0];
}
```

并给 `Timeline` 接入 `battle.rng`（可复现随机必须走同一个 RNG，否则 seed replay 失效）。

### 验证（N=300，同一阵容镜像）

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| 先手为红方 | **100%** | **51.0%** |
| 红方胜率（镜像） | **86.7%** | **50.3%** |
| Wilson 95% CI 覆盖 50% | ✗ | ✓ |

修复后镜像胜率 49.7% CI [44.0%, 55.3%]（M1 断言内跑的那次）。

### 这条被固化成了不变量测试

`tests/m1.ts` 最后一条断言：**镜像对局的 95% CI 必须覆盖 50%**。
以后任何改动能破坏对称性都会被立刻拦下。

### 顺带的实证：红区不是理论问题

用 `tieBreak: "UNRESOLVED"`（即修复前的行为，作为"未实测"的对照）跑同一组镜像：

```
先手为红 300/300 (100%)   红胜 260 / 蓝胜 40   ->  红 86.7%
```

**一个红区取不同候选假设，就把镜像胜率从 50% 推到 86.7%。**
这就是"不允许靠猜测补值"的直接证据。

## 4.5 第二轮：把实验台从"能跑"做到"能判别"

首轮 44 个实验只有 79.5% 能区分候选假设。逐个排查后发现**全是实验室接线 bug，不是理论问题**：

| 症状 | 根因 | 修复 |
|---|---|---|
| A02/A03/A10 观测恒为空 | `runStartup` 直接调用 `skill.onSoulStart`，**从未派发 `SOUL_START`/`PASSIVE_START` 事件** → `wireDummy` 注册的 handler 永不触发 | 改为 `bus.dispatch(...)`，与真实事件流一致 |
| B01/B07 防守方 handler 永不触发 | 注册用了 `range:"SELF"`，但事件以**攻击方**为 self 派发 | 改为 `range:"ENEMY"` |
| B07 触发与否无差别 | `dealDamage` 只写 trace，**从未派发 `EV.DAMAGE`** | 补派发，并新增规则 `fullyAbsorbedTriggersOnHit`（默认 false，依《回合结算过程3.0》"被护盾吸收的伤害不触发〈针女〉"） |
| A10 封印不生效 | `wireDummy` 把被动钩子注册成 `passive:false` → `suppressedPassive` 过滤不到 | 被动钩子标 `passive:true` |
| A01/B01 假设无机制 | 候选假设只是记了个 `p.__x`，实验室里没有对应实现 | 新增真实策略：`SPEED_DESC` / `TEAM_THEN_SPEED`（改用真实 teamOf+speed）/ `SELF_SIDE_FIRST` / `OTHER_SIDE_FIRST` |

**结果：可判别率 79.5% → 100%（42/42 假设检验）**，另有 2 个单假设的官方一致性校验。

| 组 | 可判别 / 假设检验 |
|---|---|
| A 开局结算顺序 | **10 / 10** |
| B 同时触发优先级 | **8 / 8** |
| C 死亡/转化/复活 | **12 / 12** |
| D 对弈竞猜 Ruleset | **12 / 12** |

> 这轮的意义：**一个"跑得动"的实验台和一个"能判别"的实验台是两回事。**
> 前者只证明代码不报错，后者才保证你在游戏里真的能看出差别。

## 4.6 「膀胱局」归因订正（重要）

修完问题 2 之后重跑普查，发现**原来的归因是错的**，实际是**两个独立原因**：

### 原因 A：我自己的 bug（已修）

`entity.effects` 不随状态到期回收，导致**治疗/护盾类 buff 永久叠加**，
辅助阵容互相奶到天荒地老。

| 阵容 | 修复前 | 修复后 |
|---|---:|---:|
| 雪女/童男/管狐 vs 赤舌/猫掌柜/缘结神（3v3 辅助） | **卡住 100%** | **卡住 0/30** |

### 原因 B：真的打不死（仍然存在）

1v1 全组合普查（12 只 × 66 对 × 20 局 = 1320 局，`maxTurns=500`）：

```
总卡住率: 145/1320 = 11.0%
其中 7 对为 100% 卡住
```

抽 童男(212) vs 祸津神(570) 逐技能核对：

```
童男 [羽刃]      dmg=[]                  <- 无伤害
童男 [羽衣]      dmg=[] shield=1         <- 护盾
童男 [魂之祭献]  dmg=[] heal=1           <- 治疗
```

**童男的全部技能都没有伤害** —— 他是纯辅助/复活型式神。
在 1v1 里他永远杀不死对手，而对手也杀不穿他的治疗 → 无限局。

**这不是 bug，是游戏本身就需要「残局加速机制」的原因**：
战斗随时间推进持续增伤 + 降低治疗量，最终由存活数/剩余生命判胜。
这正是 **D 组 12 个实验要测的东西**，也正是社区工具（平安志）报"膀胱局模拟不全"的同一件事。

### 现在的处理

`runner/monte-carlo.ts` 提供 `turnLimitSensitivity()`：
同一阵容在 `maxTurns ∈ {100, 300, 800, 2000}` 下各跑一遍，
报告胜率漂移量与卡住数的变化 —— **这是 D 组未实测时唯一诚实的精度声明**。

### 附带发现

数据里存在 `cost: -1` 的技能（雪女「冰甲术」、童男「羽衣」）。
当前实现按"≤0 即不消耗鬼火"处理。**这个语义未对官方核实**，已列入待实测清单。
